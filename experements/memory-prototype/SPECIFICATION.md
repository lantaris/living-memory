# SPECIFICATION

Техническое описание прототипа: форматы данных, алгоритмы, политики, интерфейсы.

## 1. Формат данных

### memory/core.json — ядро

```json
{
  "user": {"name": null, "role": null, "style": null},
  "preferences": {"likes": [], "dislikes": []},
  "goals": [],
  "meta": {"version": 1, "updated_at": null, "compressions": 0}
}
```

- `user` — имя, роль, стиль общения.
- `preferences.likes` / `dislikes` — списки без дублей.
- `goals` — активные долгосрочные цели.
- `meta` — служебное: версия схемы, время последнего обновления, счётчик сжатий.

### memory/tasks.json — задачи

JSON-массив записей:

```json
[{"topic": "...", "status": "open|in-progress|done", "resolved": ["..."], "open": ["..."], "updated_at": "..."}]
```

- Запись создаётся при упоминании темы, обновляется при upsert по `topic`
  (регистронезависимо, с фаззи-слиянием похожих тем, см. §3.1).
- Статусы: `open` (ничего не решено), `in-progress` (есть решение и/или остаток),
  `done` (тема закрыта). Записи со статусом `done` **сохраняются**: их `resolved` —
  это решения, уже принятые пользователем, они важны для живой модели. В контекст
  done-темы подаются компактной секцией `CLOSED TOPICS` (см. §5).
- `resolved` и `open` — **массивы строк**; новые элементы добавляются к
  существующим (union с точным дедупом), старые не удаляются. Каждый элемент —
  сжатая формулировка; это осознанный размен: замена не выражается, зато дельты
  от LLM не затирают накопленное.

### memory/loss_log.jsonl — журнал потерь

По одной записи на вытесненное сообщение, которое сжатие не использовало:

```json
{"ts": 1700000000.0, "role": "user", "text": "...", "reason": "not_used_by_compression", "indexed": true}
```

- Пишутся только реплики пользователя длиной ≥ 15 символов (`LOSS_MIN_CHARS`).
  Ответы ассистента производны и восстановимы из индекса — журнал с ними стал бы
  свалкой. Приватные сообщения не журналируются никогда (политика, см. §2).
- «Использовано» определяется полем `used` из патча сжатия (см. §4); при его
  отсутствии — консервативный лексический fallback.
- Сюда же пишутся события нормализации патча (`role: "patch"`, `indexed: false`):
  обрезки по лимитам (`patch:truncated:*`), отклонения (`patch:rejected:*`),
  вытеснение задач по лимиту количества (`patch:rejected:task_cap:*`).

### memory/pending.jsonl — очередь подтверждения

Неуверенные факты из поля `uncertain` патча сжатия:

```json
{"id": 1, "ts": 1700000000.0, "kind": "goal|like|dislike|task|other", "text": "...", "status": "pending", "resolved_at": 1700000001.0}
```

- `store.resolve_pending(id, approve)`: approve применяет факт по `kind`
  (goal → goals, like/dislike → preferences, task → тема в tasks, иной kind —
  подтверждается без применения); reject ставит `status="rejected"`.
- Записи никогда не удаляются — это аудит решений пользователя.

### memory/recent/ — оперативка по сессиям

По одному сообщению на строку; у каждой сессии свой файл:

```
memory/recent/<sessionID>.jsonl     — сессия (имя файла санитизируется)
memory/recent.jsonl                 — legacy-путь: сессия "default"
```

```json
{"id": "a1b2c3d4e5f6", "role": "user|assistant", "content": "...", "ts": 1700000000.0, "private": true?}
```

- Жёсткий лимит `recent_limit` (по умолчанию 10) на сессию. При добавлении
  лишние старые сообщения вытесняются.
- У сообщений есть `id` (нужен для безопасной ротации: сжатие удаляет только
  фактически сжатые id, а не перезаписывает хвост снапшотом).
- Старые сообщения без `id` нормализуются при чтении (`legacy-…`).
- Флаг `private` — см. политику приватности.

### memory/tasks.json — сессии

Записи задач содержат дополнительные поля:

```json
{"topic": "...", "session_id": "ses_abc", "session_label": "Firmware", "status": "...", "resolved": ["..."], "open": ["..."], "updated_at": "..."}
```

- `session_id`/`session_label` — какой сессии принадлежит тема (label —
  заголовок сессии, fallback — id). Записи без полей = legacy (сессия `default`).
- Сжатие сессии обновляет только свои записи; фаззи-слияние тем работает
  в пределах сессии (чужие темы не перетираются).
- Лимит количества (10 открытых + 10 закрытых) — общий на проект.

### memory/index.db — полный индекс (SQLite)

```sql
CREATE TABLE history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    role TEXT NOT NULL,
    content TEXT NOT NULL,
    ts REAL NOT NULL,
    private INTEGER NOT NULL DEFAULT 0,
    session_id TEXT,
    session_label TEXT
);
CREATE INDEX idx_history_ts ON history(ts);
```

- Пишутся все не-приватные сообщения в исходном виде; для каждого — сессия.
- Режим WAL + busy_timeout: параллельные чтение/запись без сбоев.
- Возврат детали: `MemoryStore.search(query)` — LIKE-поиск, новые записи первыми;
  в выдаче `session_id`/`session_label`.
  FTS5 — очевидный следующий шаг, на первом этапе не нужен.

### Потокобезопасность

- Все записи JSON/JSONL атомарны (temp-файл + `os.replace`): читатель никогда
  не видит половину файла.
- Мутации (`append`, применение патча, `resolve_pending`) идут под файловым
  lock (`fcntl.flock` на `memory/.lock`) — сериализация между процессами.
- Сжатие держит lock только на фазе применения патча (LLM-вызов — вне lock);
  перед применением хвост перечитывается, удаляются только сжатые `id`.
- Плагин дополнительно сериализует мутации очередью в процессе OpenCode.

## 2. Политика приватности

- Сообщение с флагом `private` попадает только в оперативку (нужно для текущего
  диалога) и НЕ попадает ни в `index.db`, ни в сжатие, ни в ядро/задачи.
- После вытеснения из оперативки приватное сообщение исчезает навсегда.
- При сжатии приватные сообщения отфильтровываются до вызова LLM (`compress.py`),
  и повторно игнорируются провайдером как защита от ошибки.

## 3. Алгоритм сжатия (compress.py)

Триггер (`maybe_compress`): оперативка заполнена до `recent_limit`.

Проход (`run_compression`):

1. `to_compress = recent[:-keep_recent]`, `keep = recent[-keep_recent:]`,
   где `keep_recent = recent_limit // 2` (5 по умолчанию).
2. Приватные отсеиваются; оставшееся уходит в `provider.summarize(core, tasks, messages)`.
3. Ответ LLM (строгий JSON): патч для ядра, upsert-записи для задач, `notes`
   (2–3 строки — человекочитаемый конспект прохода, в файлы памяти не пишется).
4. Патч ядра вливается рекурсивно (`deep_merge`): словари — по ключам, списки —
   с дедупликацией, `null` и пустые значения не затирают существующее.
5. Задачи обновляются upsert-ом по `topic` **в пределах сессии**; `done`-записи
   сохраняются (решения важны). Новые записи помечаются `session_id`/`session_label`.
6. Из оперативки сессии удаляются только фактически сжатые `id` (перечитывание
   под lock); сообщения, пришедшие во время сжатия, остаются.
7. `meta.compressions` и `meta.updated_at` обновляются.

Разрешение противоречия манифеста: «оперативка хранит N=10 сообщений» и «сжатие
каждые 5 обменов с удалением сжатого» несовместимы (после сжатия окно пусто или
превышает лимит). Принято: лимит окна жёсткий, сжимается только старейшая
половина, последние 5 сообщений всегда остаются дословно как горячий хвост.

### flush на границе сессии

`flush(store, provider, session_id=…)` = `run_compression(keep_recent=0)`: досжимает
оперативку **своей сессии** (включая горячий хвост), чтобы незакрытые факты
попали в ядро/задачи, а не оставались только в индексе; соседние сессии не
затрагиваются. Вызывается при закрытии сессии.

### 3.1. Нормализация патча (normalize.py)

Слой поверх конвейера: после ответа LLM и ДО применения патча каждый его элемент
проходит нормализацию; все отступления логируются в `loss_log.jsonl` с причиной
(`role: "patch"`) — ничего не отклоняется молча.

- **Лимиты длины**: goal/like/dislike ≤ 100 символов, topic ≤ 60, каждый элемент
  resolved/open ≤ 120. Обрезка по границе слова; пустые элементы отклоняются.
- **Лимиты количества**: применённые задачи — не более 10 открытых + 10 закрытых;
  при превышении вытесняются самые старые по `updated_at` (с записью в журнал).
- **Строгие категории**: `user.style` удаляется из патча (стиль — мета);
  неизвестные ключи `core` отклоняются; задача без topic отклоняется.
- **Дедупликация тем**: ключ темы нормализуется (регистр, служебные префиксы,
  пунктуация); дополнительные темы сливаются с существующими при точном
  совпадении ключа или совпадении ≥ 50% ключевых слов (длиннее 4 символов).
- **Строка → массив**: поле resolved/open, пришедшее строкой с `;`, разбивается
  на элементы — хвосты списков больше не теряются при обрезке.

## 4. Промпт сжатия

Константа `COMPRESSION_PROMPT` в `compress.py`. Требует строгий JSON без
markdown-обёрток со схемой `{core, tasks, uncertain, used, notes}`. Инструкции:
извлекать только устойчивый смысл (факты, изменения предпочтений, решения, новые
цели, открытые вопросы), не пересказывать диалог, никогда не включать приватное.
Строгие правила: решения — только в `tasks[].resolved`; открытое — только в
`tasks[].open`; тема закрывается только при пустом open; предпочтения — только в
`likes/dislikes`; `user.style` запрещён; мимоходное не хранится (примеры мусора);
одна тема на рабочий поток, без синонимов и переводов существующих тем; лимиты
длины и количества (см. §3.1) продублированы в промпте. При конфликте нового
факта со старым побеждает свежий, смена отражается явно («Rust (switched from
Python)»).

- `uncertain` — важные, но сомнительные факты: уходят в `pending.jsonl`, не в
  core/tasks (правило «never duplicate» в промпте).
- `used` — номера входных сообщений (1-based), из которых извлечён любой факт;
  на их основе ведётся журнал потерь (см. §1).
- `meta` из патча игнорируется: служебные поля меняет только конвейер.
- При сжатии сессии в промпт добавляется session-нота: чужие задачи — только
  контекст, их нельзя менять/сливать; новые задачи принадлежат текущей сессии.

## 5. Инъекция в контекст (inject.py)

`build_system_prompt(store, session_id=None, session_label=None)`:

- **без сессии (legacy/CLI)**: `# CORE MEMORY` → `# OPEN TASKS` (все задачи) →
  `# CLOSED TOPICS` → `# RECENT MESSAGES` (default-хвост);
- **с сессией**:

```
# CORE MEMORY (shared)         — core.json, общий
# MY TASKS (session: <label>)  — задачи своей сессии (status != done)
# CLOSED TOPICS (this session) — решения своей сессии, компактно
# OTHER SESSIONS               — сводка: `- [label] topic — status` (read-only)
# RECENT MESSAGES (this session) — только хвост своей сессии
```

Соседние сессии видны сводкой (их `resolved`/`open` в промпт не попадают —
детали достаются через `memory_search` по общему индексу). Это и есть весь
контекст, передаваемый LLM, — не полная история.
`full_history_text(store)` существует только для сравнения метрик.

## 6. Интерфейс LLMProvider (llm.py)

```python
class LLMProvider(ABC):
    def summarize(self, core: dict, tasks: list, messages: list) -> dict: ...
```

- `MockProvider` — детерминированный офлайн-дублёр: извлекает факты regex-эвристиками
  по русским конструкциям («меня зовут», «не люблю», «Решили:», «Осталось:»,
  «Тема:»). Проверяет конвейер, а не качество сжатия; не является частью идеи.
- `OpencodeCLIProvider` — вызывает `opencode run <промпт>` и извлекает JSON из
  вывода (`extract_json`).
- Выбор: `get_default_provider()` — `MEMORY_LLM_PROVIDER=opencode` включает CLI,
  иначе Mock.

## 7. Модули и API

| Модуль | Публичное API |
|--------|---------------|
| store.py | `MemoryStore(base_dir, recent_limit)`: `read/write_core`, `read/write_tasks`, `read/write_recent(session_id)`, `append_message(role, content, private, session_id, session_label)`, `session_recent_path`, `locked()`, `history_count`, `search` (с сессиями), `log_loss/read_loss_log`, `append_pending/read_pending/write_pending/resolve_pending` |
| compress.py | `build_compression_prompt(…, session_label)`, `run_compression(…, session_id, session_label)`, `maybe_compress(…)`, `flush(…)`, `apply_core_updates`, `apply_task_updates(…, session_id, session_label)` |
| inject.py | `build_system_prompt(store, session_id, session_label)`, `full_history_text` |
| llm.py | `LLMProvider.summarize(core, tasks, messages, session_label)`, `MockProvider`, `OpencodeCLIProvider`, `get_default_provider` |

CLI-фасад плагина (`cli.py`): глобальные флаги `--session`/`--session-label` до
команды (`append`, `context`, `compact [--if-full]`, `flush`, `search`, `status`).

## 8. Известные ограничения

- Качество сжатия определяется промптом и LLM; возможна потеря важного. Компенсация
  — `index.db` и `search`. Потери тихие, но обратимые (проверено: `test_loss_conflict.py`).
- Протокол патча сжатия поддерживает только добавление: при конфликте список
  накапливает оба значения, хронологию обеспечивает пометка от LLM
  (операции замены/удаления в патче — кандидат на следующий шаг).
- Журнал потерь и отбор `uncertain` зависят от дисциплины модели: она может
  пометить `used` щедро (журнал опустеет) или продублировать uncertain-факт в
  core/tasks (тогда reject не очистит конспект). Мок детерминирован; про
  реальную LLM см. NOTES §8.
- Мок-сжатие сканирует и реплики ассистента (режим B): советы ассистента могут
  попасть в цели/задачи как факты пользователя. LLM-сжатие этого не делает.
- Кто решает, что важно, — LLM; ручная правка слоёв пока не предусмотрена (следующий шаг).
- `search` — LIKE без учёта морфологии; для прототипа достаточно.
- Многопользовательский режим не поддержан: память — на проект, не на человека.
- Сессии одного проекта делят `core.json` (факты о пользователе); разные люди за
  одним проектом будут смешивать ядро — это осознанное ограничение.
- Параллельные сжатия сериализуются файловым lock; LLM-вызовы при этом не
  экономятся (каждое сжатие — отдельный вызов).
