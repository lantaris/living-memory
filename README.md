# living-memory

> **Статус:** продукт переезжает на имя `living-memory`; в npm пока не опубликован
> (`opencode-memory` там занят чужим пакетом), установка — из репозитория или
> локального пути. Планируется адаптер для Hermes (MemoryProvider) поверх того же
> движка.

Layered living memory for [OpenCode](https://opencode.ai) agents: instead of
replaying the whole history, the agent keeps a compressed model of the user and
the project across sessions. The plugin is a thin TypeScript layer that drives a
proven Python engine through a subprocess bridge.

Что это даёт:

- **память между сессиями**: ядро (кто пользователь), задачи (что решено и что
  осталось), оперативка (последние сообщения) живут в файлах проекта;
- **несколько сессий параллельно**: у каждой сессии свой горячий хвост и свои
  задачи; соседние сессии видны сводкой (`OTHER SESSIONS`) и через поиск;
- **сжатие на лету**: когда оперативка заполняется, LLM-конспект переносит
  смысл в ядро/задачи, а сообщения вытесняются;
- **журнал потерь**: всё, что не попало в конспект, видно в `loss_log.jsonl`
  с причиной и признаком обратимости (полная история — в `index.db`);
- **инструмент `memory_search`**: агент сам ищет детали в полной истории,
  когда их нет в конспекте (например, мимоходные факты); поиск — на FTS5
  (фолбэк — LIKE), в выдаче — метка сессии;
- **скилл-инструкция**: в пакете лежит `skills/living-memory/SKILL.md` —
  агент знает, когда и как звать `memory_search`;
- **flush при завершении сессии**: незакрытые факты досжимаются, а не теряются;
- **очередь подтверждения**: неуверенные факты попадают в `pending.jsonl`, а не
  решаются молча; просмотр и подтверждение — командой `pending` (CLI) и
  инструментом `memory_pending` у агента.

## Несколько сессий (firmware + app)

Можно вести две (и больше) сессий параллельно, над разными частями проекта:

- **хвост у каждой сессии свой** — `memory/recent/<sessionID>.jsonl`; чужие
  реплики не подмешиваются в диалог;
- **задачи маркируются сессией** (`session_id`, `session_label` — заголовок
  сессии); в промпте своя сессия видит `MY TASKS` полностью, соседей —
  сводкой `OTHER SESSIONS` (label + тема + статус);
- **сжатие и дедупликация — только внутри своей сессии**: чужую задачу
  («настройка» у соседа) не перетрёт и не сольёт;
- **общее — доступно всем**: `core.json` (факты о пользователе), `index.db`
  (полная история), `loss_log`/`pending`; `memory_search` ищет по всем сессиям
  и показывает метку (`[user @ ts | Firmware]`);
- **параллельная работа безопасна**: мутации сериализуются (очередь в плагине
  + SQLite-мьютекс), записи атомарные, SQLite в WAL; сжатие удаляет из хвоста
  только фактически сжатые сообщения (по id) — сообщение, пришедшее во время
  сжатия, не теряется.

Subagent-сессии в память не пишутся. Старые данные без меток трактуются как
сессия `default` (совместимость).

## Установка

Требования:

- OpenCode с поддержкой плагинов;
- **Python 3.10+** — интерпретатор ищется автоматически (`python3` → `python`
  → `py -3`); свой путь можно задать опцией `pythonBin` или переменной
  `MEMORY_PLUGIN_PYTHON`;
- Node.js 22+.

Пакет пока **не опубликован** в npm — установка из репозитория или локального пути:

```bash
# локальный клон
git clone <репозиторий> && cd living-memory && npm install && npm run build

# из git — когда появится публичный репозиторий living-memory
# (сейчас он не создан — используйте локальный клон выше)
```

Подключение в `opencode.json` (проект или глобальный):

```json
{
  "$schema": "https://opencode.ai/config.json",
  "plugin": ["<путь-до-репозитория>/dist/src/index.js"]
}
```

Опции (второй элемент кортежа):

```json
{
  "plugin": [
    ["<путь-до-репозитория>/dist/src/index.js", { "provider": "opencode", "recentLimit": 10 }]
  ]
}
```

| Опция | По умолчанию | Смысл |
|-------|--------------|-------|
| `dataDir` | `<проект>/.living-memory` | где лежат слои памяти (общий каталог проекта для обоих агентов) |
| `pythonBin` | авто (`python3`/`python`/`py -3`) | интерпретатор Python |
| `provider` | `opencode` | кто сжимает: `opencode` (LLM через `opencode run`) или `mock` (офлайн-эвристика, для тестов) |
| `recentLimit` | `10` | размер оперативки |

Перезапустите OpenCode после изменения конфига.

## Как работает

- `session.created` — регистрация сессии, память готова;
- `chat.message` — сообщение пользователя пишется в оперативку;
- `session.idle` — синхронизация ответов ассистента; если оперативка заполнена
  — запускается сжатие;
- `experimental.chat.system.transform` — в системный промпт каждого запроса
  добавляется собранный конспект (ядро + задачи + хвост);
- `experimental.session.compacting` — при встроенной Compaction OpenCode в неё
  передаётся готовый конспект, чтобы история не пересуммировалась с нуля;
- `session.deleted` и выгрузка плагина — flush;
- инструмент `memory_search` — поиск по полной истории (`index.db`, FTS5);
- инструмент `memory_pending` — очередь подтверждения: `list` / `approve` / `reject`.

**Скилл `living-memory` уже внутри пакета** — отдельная установка не нужна.
При первом запуске плагин кладёт его в `<проект>/.opencode/skills/living-memory/SKILL.md`
и сообщает об этом в `plugin.log`. Инструкция говорит агенту, когда вызывать
`memory_search` (детали из прошлых сессий, «мы это обсуждали»), а когда нет
(свежие сообщения и так в контексте; не звать на каждом ходу).

Каждый сбой моста (нет Python, таймаут, ошибка) **не блокирует сессию**:
плагин пишет строку в `<dataDir>/plugin.log` и продолжает работу без памяти.

Отключение:

- убрать плагин из `plugin` в `opencode.json`, или
- переменная окружения `MEMORY_PLUGIN_DISABLE=1` (плагин молча выключится),
- диагностика событий: `MEMORY_PLUGIN_DEBUG=1`;
- модель для сжатия через `opencode run`: `MEMORY_LLM_MODEL=<provider/model>`
  (например, `deepseek/deepseek-flash`); по умолчанию — модель OpenCode по умолчанию.

## Данные на диске

```
<dataDir>/
  plugin.log        журнал плагина (ошибки, решения хуков)
  memory/
    core.json       ядро: пользователь, предпочтения, цели
    tasks.json      задачи: темы, статусы, решения, открытые пункты (+ session_id/метка)
    recent/         оперативка по сессиям: recent/<sessionID>.jsonl
    recent.jsonl    legacy-путь оперативки для сессии "default" (совместимость)
    loss_log.jsonl  журнал потерь и событий нормализации
    pending.jsonl   очередь подтверждения (неуверенные факты; approve/reject)
    index.db        полная история (SQLite) — восстановление деталей
```

## Честные ограничения

Это упаковка проверенного прототипа; ниже — то, что известно по его
экспериментам (цифры и детали — в истории разработки прототипа, локальный
архив; в npm-пакет не входит).

**Дизайн (так задумано):**

- **Мимоходные детали теряются.** «Кот Персик», «сериал», «кофе» по правилам
  сжатия не хранятся в конспекте. Модель честно отвечает «не знаю» и НЕ
  выдумывает (0 галлюцинаций в retention-тестах). Такие детали доступны через
  `memory_search` — и, будучи найденными, могут позже закрепиться в конспекте
  (проверено в живом OpenCode: хобби нашлось поиском и попало в `likes` при
  следующем сжатии).
- **Поиск — FTS5 по токенам** (морфологии нет): «SQLite» найдётся, «пластинки»
  при оригинале «винил» — не обязательно. Поиск общий по всем сессиям проекта
  (в выдаче есть метка сессии); на сборках SQLite без FTS5 включается LIKE-фолбэк.
- **Стоимость на коротких диалогах.** На коротких диалогах конспект не даёт
  выигрыша (в замерах: 67% от полной истории после нормализации, но 95% до
  неё — экономия появляется с длиной). Каждое сжатие — вызов LLM.
- **Ядро общее на проект, не на человека.** `core.json` один для всех сессий
  проекта: два разных пользователя за одним проектом смешают факты о себе.
- **Лимит задач 10+10.** Открытые и закрытые темы ограничены; при долгой жизни
  проекта самые старые вытесняются — это видно в `loss_log.jsonl`
  (`patch:rejected:task_cap:*`).
- **Пустые хвосты сессий накапливаются.** После flush файл
  `recent/<sessionID>.jsonl` остаётся пустым; гигиена (удаление) — кандидат на
  доработку.

**Зависит от модели (не баг плагина):**

- **Категоризация у LLM нестабильна.** Модель-сжатие иногда путает «решения» и
  «открытые задачи», сливает похожие темы, кладёт задачи в предпочтения. Это
  свойство модели, а не плагина; нормализация ловит формат (лимиты, дубли,
  style), но не смысл.
- **«Uncertain не в конспекте» зависит от дисциплины модели.** Промпт требует
  не дублировать неуверенные факты в ядро/задачи, но модель может это
  нарушить; журнал покажет событие, однако гарантии нет.
- **Гарантии памяти зависят от качества модели сжатия.** На слабых моделях
  конспект шумнее; `pending.jsonl` и `loss_log.jsonl` позволяют это увидеть.

**Инфраструктура и компромиссы:**

- **Скилл зависит от сканирования диска.** В текущем API OpenCode
  `PluginInput.skills` не существует (проверено на рантайме), поэтому скилл
  устанавливается файлом в `<проект>/.opencode/skills/`. OpenCode подхватывает
  скиллы при запуске: **после первой установки плагина нужен перезапуск**, чтобы
  агент увидел инструкцию. Если API появится/изменится — поведение может
  отличаться; статус установки скилла всегда виден в `plugin.log`.
- **Производительность.** Каждая операция — отдельный запуск Python; на слабых
  машинах хуки могут подтормаживать, а `flush` при выходе ждёт LLM-сжатие.
- **Стоимость при параллельных сессиях.** Каждая сессия сжимается отдельно;
  два одновременных сжатия — это два вызова LLM (они применяются по очереди,
  но токены тратятся оба).

## Проверено изнутри / не проверено

Проверено (см. `python/` и тесты прототипа):

- движок: retention-тест на диалоге из 104 сообщений, A/B/C-режимы, границы потерь;
- мост, хуки, инструменты и скилл: `npm test` (16 тестов: subprocess-мост, батч-запись,
  запись сообщений, инъекция контекста с маркерами, `memory_search` с данными и без,
  `memory_pending` на пустой очереди, деградация без Python, установка скилла,
  изоляция двух сессий, фильтр subagent-сессий);
- ядро и семантика: `pytest tests/python` (20 тестов: очередь `pending` end-to-end,
  forget-операции, капы per-session, детект uncertain-дублей, FTS5 и LIKE-фолбэк,
  конкурентность и транспорт);
- интеграция в живом OpenCode (v0.2.0, `opencode run` с системной установкой):
  раздельные хвосты двух сессий (`recent/<sid>.jsonl`), задачи с метками
  сессий, третья сессия видит соседей сводкой `OTHER SESSIONS`,
  **агент вызвал `memory_search`** и получил записи с меткой сессии; flush
  при завершении срабатывает, скилл устанавливается идемпотентно;
- живой цикл на текущей версии (OpenCode 1.18.31, deepseek-flash): запись хвоста,
  инъекция в каждый LLM-запрос (`system = 2`), **новая сессия ответила фактом из
  `core.json`** (чистое доказательство инъекции), `memory_search` вызван агентом,
  flush через вложенный `opencode run` записал факты в core и очистил хвост.

**Не проверено**: поведение у реальных пользователей в TUI-режиме, полная
встроенная компакция сессии живьём (CLI-команды для неё нет — нужен TUI или
длинный диалог), замер стоимости на длинном диалоге, Linux/macOS-раннеры CI
(включатся с репозиторием), устойчивость при смене API плагинов OpenCode.
Windows проверен на стенде (node 16/16, python 20/20), живой цикл в OpenCode
1.18.31 пройден. Проверьте остальное после установки.

## Разработка

```bash
npm install
npm run build
npm test                       # node-мост (16 тестов)
./.venv/Scripts/python -m pytest tests/python -q   # ядро (24 теста; на Linux/macOS — python -m pytest)
```

Структура: `src/` — TypeScript (config, bridge, hooks, tools, skill, index);
`python/` — движок прототипа (store, compress, inject, normalize, llm,
cli-фасад); в `src/`: `skill.ts` (установка скилла), `tools.ts` (инструмент
`memory_search`).
